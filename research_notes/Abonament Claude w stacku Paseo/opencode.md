# Abonament Claude w stacku Paseo → OpenCode: Opus + DeepSeek dla context-scout-fast

Stan researchu: **2026-09-30**. Cel: gotowe alternatywy dla `ex-machina-co/opencode-anthropic-auth`, z modelem głównym Opus z abonamentu Claude i niezależnym modelem DeepSeek dla subagenta `context-scout-fast`. Stack Paseo → OpenCode jest założeniem przekazanym przez użytkownika, a nie wynikiem inspekcji jego konfiguracji.

Metoda: wyszukiwanie zewnętrznych repozytoriów przez `gh search repos`, odczyt README i dokumentacji przez WebFetch, sprawdzenie wybranych implementacji i metadanych przez GitHub API oraz dokumentacji OpenCode przez Context7 (`/anomalyco/opencode`). Bez instalacji, uruchamiania kandydatów i zmian konfiguracji. Daty aktywności poniżej to `pushed_at`, nie `updated_at`; liczby gwiazdek są chwilowym snapshotem, nie dowodem jakości. Nie sprawdzano lokalnego repozytorium poza docelowym katalogiem notatek.

## 1. Jaki rodzaj integracji rzeczywiście zachowuje OpenCode i niezależny DeepSeek?

### Takeaway

Potrzebny jest backend zwracający **rzeczywiste wywołania narzędzi OpenCode**, a nie tylko końcową odpowiedź agenta Claude Code. Zbadane źródła pokazują dwa mosty CLI z takim mechanizmem; najlepiej dopasowany gotowy plugin to Krowli, ale zgodność całego łańcucha Paseo → OpenCode → Opus → `task` → DeepSeek pozostaje niezweryfikowana end-to-end. — [Krowli: implementacja](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/proxy.ts), [Antonio: implementacja](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/translation/cli-to-openai-stream.ts)

### Cited Findings

- **Natywny model per rola istnieje w OpenCode.** Agent może mieć własne `model`, prompt, tryb `subagent` i permissions. W sprawdzonym `task.ts` wybór modelu to `next.model ?? model rodzica`: jawnie ustawiony model subagenta wygrywa nad modelem głównym. To mechanizm potrzebny dla `context-scout-fast`; samo ustawienie globalnego Opusa nie musi zmieniać modelu tej roli. — [Dokumentacja agentów](https://opencode.ai/docs/agents/), [task.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts), [agent.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/agent/agent.ts)
- **Provider modelu z narzędziami po stronie OpenCode:** adapter przyjmuje definicje narzędzi, emituje `tool_calls`/`tool_use`, OpenCode wykonuje narzędzie i odsyła wynik. Krowli ma taki adapter: rejestruje narzędzia klienta jako MCP, wyłącza built-ins Claude przez `tools: []`, parkuje proces SDK i rozwiązuje oczekujące wywołania dopiero po otrzymaniu wyników klienta. Technicznie SDK nadal utrzymuje wewnętrzną sesję i kontynuację, ale właścicielem wykonania narzędzi i delegowania pozostaje OpenCode. — [proxy.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/proxy.ts), [bridge-pool.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/bridge-pool.ts)
- **Worker invocation:** OpenCode wywołuje narzędzie/plugin albo model-fasadę, za którą Claude Code sam wykonuje Read/Bash/Task/MCP. Nazwa „provider” nie zmienia właściciela pętli. Przykłady: `leohenon/opencode-claude-cli` i `JulianBeaulieu/opencode-claude-bridge`; pierwszy jawnie opisuje narzędzia Claude jako display-only transcript, drugi przyznaje, że to tool-level bridge, a nie pełny backend providera. — [leohenon README](https://github.com/leohenon/opencode-claude-cli/blob/master/README.md), [Julian README](https://github.com/JulianBeaulieu/opencode-claude-bridge/blob/main/README.md)
- **OAuth impersonation / bezpośredni klient z tokenem abonamentu:** plugin lub proxy pobiera tokeny Claude i wysyła własne żądania HTTP do Anthropic, modyfikując tożsamość żądania i nazwy narzędzi. OpenCode może zachować całą pętlę, ale to nie jest wykonanie przez oficjalny CLI. Tak działają `griffinmartin/opencode-claude-auth`, `eysenfalk/opencode-claude-subscription` oraz ścieżka Claude w CLIProxyAPI. — [griffinmartin: opis techniczny](https://github.com/griffinmartin/opencode-claude-auth#how-it-works-technical), [eysenfalk: diagram](https://github.com/eysenfalk/opencode-claude-subscription#how-it-works), [CLIProxyAPI ClaudeExecutor](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/runtime/executor/claude_executor.go)
- **MCP-shaped tool alias nie jest automatycznie serwerem MCP.** W pluginach OAuth to zmiana nazw na drucie. W Krowli i Antonio to faktyczny most MCP pomiędzy CLI a narzędziami klienta, z różnym modelem kontynuacji. — [eysenfalk README](https://github.com/eysenfalk/opencode-claude-subscription#what-changes-on-the-wire), [Krowli proxy.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/proxy.ts), [Antonio mcp-bridge.ts](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/tools/mcp-bridge.ts)
- **ACP jest protokołem agenta, nie automatycznie providerem modelu.** Dokumentacja OpenCode opisuje `opencode acp` jako agent server dla klientów ACP. Adapter Claude ACP daje klientowi agenta Claude; nie podmienia przez sam fakt istnienia endpointu ACP jednego modelu w OpenCode. — [OpenCode ACP](https://opencode.ai/docs/acp/), [Claude Agent ACP](https://github.com/agentclientprotocol/claude-agent-acp)
- **Wykonalność auth ≠ oficjalnie wspierane użycie abonamentu.** SDK Anthropic uruchamia binary Claude Code i posiada jego agent loop. Ta sama oficjalna dokumentacja mówi, że bez wcześniejszej zgody zewnętrzni twórcy nie mogą oferować logowania claude.ai ani jego limitów w swoich produktach, również opartych na Agent SDK. Sam most CLI/SDK nie dowodzi zgody Anthropic na wykorzystanie abonamentu w OpenCode. — [Oficjalny Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### Inferences

- Jeśli most oddaje `task` do OpenCode, OpenCode może uruchomić `context-scout-fast` z jego własnym providerem DeepSeek. Ustawienie Claude jako głównego modelu i DeepSeek w definicji subagenta wystarcza na poziomie architektury OpenCode; potrzebna jest jeszcze poprawna obsługa round-trip przez most. — [Model resolution](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts), [Krowli regression](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/test/parallel-tools-regression.ts)
- Jeżeli narzędzie `Task` wykonuje Claude CLI, jest to delegowanie Claude Code, nie natywne `task` OpenCode. Nie ma wtedy podstaw, by uznać, że wybrany zostanie model z OpenCode przypisany do `context-scout-fast`. Ręcznie uruchamiana sesja DeepSeek w OpenCode może nadal działać, ale nie potwierdza automatycznego delegowania z głównego Opusa. — [leohenon: wykonanie](https://github.com/leohenon/opencode-claude-cli/blob/master/src/claude-cli.ts), [OpenCode task.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts)

### Gaps

- Nie ustalono wersji OpenCode ani sposobu uruchamiania jego serwera przez Paseo. To istotne, bo kandydaci używają różnych generacji plugin API; Krowli i eysenfalk celują w V2, podczas gdy inni pokazują konfigurację V1. — [Krowli requirements](https://github.com/Krowli/opencode-claude-bridge#requirements), [eysenfalk tested with](https://github.com/eysenfalk/opencode-claude-subscription#tested-with), [leohenon config](https://github.com/leohenon/opencode-claude-cli#configure)
- Nie wykonano testu `Opus → native task → context-scout-fast → DeepSeek → wynik Opus`. Przeanalizowany test Krowli używa mocka SDK, sprawdza round-trip równoległych `read` oraz rejestrację/annotations `task` i `subagent`; nie jest dowodem rzeczywistego wywołania DeepSeek. — [Test źródłowy](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/test/parallel-tools-regression.ts)
- Nie potwierdzono zgody Anthropic dla żadnego badanego mostu OpenCode. Nie oszacowano częstotliwości blokad kont ani nie oceniano metod obchodzenia detekcji. — [Oficjalne ograniczenie SDK](https://code.claude.com/docs/en/agent-sdk/overview)

## 2. Które gotowe projekty warto rozważyć i jak dojrzałe są ich mechanizmy?

### Takeaway

Ranking według dopasowania do **Opus abonamentowy + natywne role OpenCode z DeepSeek**, nie według popularności: **1) Krowli, 2) AntonioAEMartins, 3) griffinmartin, 4) CLIProxyAPI, 5) eysenfalk**. Pierwsze dwa naprawdę uruchamiają CLI i zwracają narzędzia do klienta; pozycje 3–5 zachowują pętlę OpenCode przez bezpośrednie HTTP/OAuth, więc nie są zmianą klasy rozwiązania względem pluginów auth. — [Krowli](https://github.com/Krowli/opencode-claude-bridge), [Antonio](https://github.com/AntonioAEMartins/claude-code-proxy), [griffinmartin](https://github.com/griffinmartin/opencode-claude-auth), [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI), [eysenfalk](https://github.com/eysenfalk/opencode-claude-subscription)

### Cited Findings

#### 1. Krowli/opencode-claude-bridge — najlepsze dopasowanie architektoniczne; eksperymentalne

- **Gotowa integracja OpenCode V2:** plugin uruchamia lokalny proxy jako child serwera OpenCode, dostarcza konfigurację providera `claude-code` przez adapter OpenAI-compatible i oznacza żądania session ID, katalogiem projektu, typem żądania i effort. Hook jest ograniczony do `providerID: "claude-code"`. — [README](https://github.com/Krowli/opencode-claude-bridge), [plugin](https://github.com/Krowli/opencode-claude-bridge/blob/main/plugin/opencode-claude-proxy.ts), [provider config](https://github.com/Krowli/opencode-claude-bridge/blob/main/config/opencode.claude-code.json)
- **Abonament:** rzeczywisty Claude Agent SDK → lokalny `claude`, z istniejącym logowaniem; proxy nie kopiuje tokenów do własnego HTTP klienta. Autor celuje w Claude Max. To deklarowana obsługa techniczna, nie potwierdzenie autoryzacji produktu przez Anthropic. — [README: architecture/requirements](https://github.com/Krowli/opencode-claude-bridge#requirements), [auth-env.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/auth-env.ts)
- **Własność narzędzi:** `tools: []` wyłącza built-ins; definicje OpenCode są wystawiane przez SDK MCP server `opencode`; callback parkuje wywołanie i czeka na wynik wykonany przez OpenCode. Następne żądanie z wynikami odnajduje parked bridge i rozwiązuje promises. Aliasowanie kieruje znane nazwy built-ins do narzędzi OpenCode. — [proxy.ts: bridge i opcje query](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/proxy.ts#L822-L930), [MCP bridge](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/proxy.ts#L1220-L1369), [bridge-pool.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/bridge-pool.ts)
- **MCP:** `isolateMcp: true` usuwa konkurujące serwery i konektory Claude-side z tej ścieżki. Klient przekazuje narzędzia OpenCode, a most odsyła ich wywołania do klienta. Kod zachowuje oryginalny JSON Schema w `tools/list`, zamiast polegać tylko na konwersji do Zod. To silniejszy dowód niż deklaracja „tools supported”. — [proxy.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/proxy.ts), [query.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/query.ts), [audyt autora](https://github.com/Krowli/opencode-claude-bridge/blob/main/docs/AUDIT.md)
- **Role/task:** test uwzględnia `task` i `subagent`, a kod nie wykonuje natywnych narzędzi Claude. Architektura nadaje się do utrzymania roli DeepSeek w OpenCode; test sprawdza jednak annotations tych dwóch narzędzi, nie prawdziwe wykonanie roli. — [parallel-tools-regression.ts](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/test/parallel-tools-regression.ts)
- **Dojrzałość:** 0 gwiazdek w snapshotcie; ostatni push 2026-09-27; release **v1.0.2 z 2026-09-27**. Są offline regression tests i smoke-test, ale bardzo krótka historia/publiczna adopcja. README ogranicza target do V2 i macOS; inne platformy określa jako nietestowane. — [Metadane repo](https://api.github.com/repos/Krowli/opencode-claude-bridge), [release](https://github.com/Krowli/opencode-claude-bridge/releases/tag/v1.0.2), [requirements](https://github.com/Krowli/opencode-claude-bridge#requirements), [tests](https://github.com/Krowli/opencode-claude-bridge/tree/main/proxy/test)
- **Niepewność:** macOS/keychain i uruchamianie z procesu sesji użytkownika to istotny szczegół dla serwera odpalonego przez Paseo. Nie potwierdzono Linux/headless ani zgodności wersji z istniejącym stackiem. Oświadczenia autora w `docs/AUDIT.md` nie są niezależnym audytem. — [README: why this layout](https://github.com/Krowli/opencode-claude-bridge#why-this-layout), [AUDIT.md](https://github.com/Krowli/opencode-claude-bridge/blob/main/docs/AUDIT.md)

#### 2. AntonioAEMartins/claude-code-proxy — uniwersalny backend CLI z client-side tool calling

- **Mechanizm:** lokalny proxy Node, endpointy Anthropic `/v1/messages` i OpenAI `/v1/chat/completions`; każde żądanie uruchamia nowy `claude --print`, bez trwałej sesji. README jawnie deklaruje Claude Max i istniejące logowanie CLI. — [README](https://github.com/AntonioAEMartins/claude-code-proxy)
- **To nie tylko worker:** kod wyłącza built-ins przez `--tools ''`, ustawia strict MCP i buduje MCP bridge z definicji narzędzi klienta. Most zwraca placeholder `pending`, natomiast translator kończy odpowiedź po pierwszym modelowym `tool_use`, zanim kontynuacja z placeholderem trafi do klienta; route w `finally` zabija CLI. OpenCode otrzymuje `tool_calls`, wykonuje narzędzie i wysyła nową historię. — [args-builder.ts](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/cli/args-builder.ts), [mcp-bridge.ts](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/tools/mcp-bridge.ts), [stream translator](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/translation/cli-to-openai-stream.ts), [route](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/routes/openai-chat-completions.ts)
- **Task/DeepSeek:** endpoint przyjmuje arbitrary function tools i historię `tool`/`tool_calls`; to daje możliwość przekazania natywnego `task` OpenCode bez zmiany modelu subagenta. To wniosek z kontraktu, nie gotowy, przetestowany przykład OpenCode + DeepSeek. — [convertTools/convertMessages](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/routes/openai-chat-completions.ts)
- **MCP/limity:** opcjonalny registry MCP uruchamia serwery po stronie proxy/CLI, co trzeba odróżniać od client-executed tools OpenCode. Brak vision, sampling ignorowany, `max_tokens` tylko advisory; historia jest przekładana do promptu, nie utrzymywana jak natywna sesja API. README opisuje nieinteraktywny tryb permissions. — [README limitations i MCP](https://github.com/AntonioAEMartins/claude-code-proxy#limitations), [translation](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/translation/anthropic-to-cli.ts), [args-builder](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/cli/args-builder.ts)
- **Dojrzałość:** 29 gwiazdek; ostatni push 2026-05-03; zapytanie GitHub Releases zwróciło pustą listę. Nie jest gotowym pluginem lifecycle OpenCode/Paseo: jest gotowym proxy, którego kompatybilny endpoint trzeba połączyć z providerem. — [Metadane](https://api.github.com/repos/AntonioAEMartins/claude-code-proxy), [Releases API](https://api.github.com/repos/AntonioAEMartins/claude-code-proxy/releases), [OpenCode custom providers](https://opencode.ai/docs/providers/#custom-provider)
- **Niepewność:** natywny `task`, równoległość, długie historie i zachowanie po compaction nie zostały sprawdzone w OpenCode. Restart CLI na każdy round-trip i tekstowa rekonstrukcja kontekstu są słabszą integracją sesji niż parked bridge Krowli. — [README how it works](https://github.com/AntonioAEMartins/claude-code-proxy#how-it-works), [Krowli bridge-pool](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/bridge-pool.ts)

#### 3. griffinmartin/opencode-claude-auth — dojrzała alternatywa auth, ale ta sama klasa OAuth

- **Mechanizm:** własny `auth.loader` i custom `fetch`; odczyt Keychain/credentials Claude Code, odświeżanie OAuth, bezpośrednie żądania API, transformacje nazw narzędzi i system promptu. CLI bywa fallbackiem odświeżenia, nie harness-em prowadzącym każde zadanie. — [README how it works](https://github.com/griffinmartin/opencode-claude-auth#how-it-works-technical)
- **Abonament i role:** technicznie wykorzystuje istniejące tokeny Pro/Max, a wykonanie narzędzi pozostaje w OpenCode. Natywny `task` i osobny model DeepSeek mają więc właściwą architekturę; ograniczenia są w translacji/akceptacji żądań OAuth, nie w zastąpieniu pętli Claude CLI. — [README](https://github.com/griffinmartin/opencode-claude-auth), [OpenCode task](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts)
- **MCP/ograniczenia:** tłumaczenie nazw narzędzi i SSE, naprawa historii `tool_use`/`tool_result` po compaction; README odnotowuje extra usage dla długiego kontekstu i brak oficjalnej zgody na używanie abonamentowych tokenów w innych klientach. — [README technical / long context / disclaimer](https://github.com/griffinmartin/opencode-claude-auth)
- **Dojrzałość:** 1291 gwiazdek, push 2026-09-22, release **v2.2.1 z 2026-09-22**; wyraźnie większa adopcja niż mosty CLI znalezione dla OpenCode. Dokumentowane przykłady używają `plugin` V1. — [Metadane](https://api.github.com/repos/griffinmartin/opencode-claude-auth), [release](https://github.com/griffinmartin/opencode-claude-auth/releases/tag/v2.2.1), [installation](https://github.com/griffinmartin/opencode-claude-auth#installation)

#### 4. router-for-me/CLIProxyAPI — aktywna infrastruktura proxy, lecz nie CLI subprocess dla Claude

- **Mechanizm zweryfikowany w kodzie:** `ClaudeExecutor` to stateless executor Anthropic Messages API. `PrepareRequest` umieszcza credentials w nagłówku, a `HttpRequest` wykonuje request przez HTTP client. Nazwa „CLIProxyAPI” i hasło „Claude Code support” nie oznaczają uruchamiania Claude CLI w tej ścieżce. — [claude_executor.go](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/runtime/executor/claude_executor.go)
- **Abonament/tools:** README deklaruje Claude OAuth, streaming i function calling. Dokumentacja griffinmartin podaje gotowe połączenie OpenCode z Claude-compatible endpointem proxy przez jego wbudowany provider Anthropic. Narzędzia wykonuje klient OpenCode; sam proxy nie dostarcza MCP runtime dla projektu OpenCode. — [README](https://github.com/router-for-me/CLIProxyAPI#overview), [OpenCode integration example](https://github.com/griffinmartin/opencode-claude-auth#alternative-cliproxyapi-plugin-not-required)
- **Role:** może zachować native task i DeepSeek poprzez osobny provider, ale dla Claude jest nadal direct HTTP/OAuth. Desktopowe opakowania takie jak VibeProxy/Quotio nie zmieniają tego mechanizmu, jeśli ich backend to CLIProxyAPI. — [README ecosystem](https://github.com/router-for-me/CLIProxyAPI#who-is-with-us), [executor](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/runtime/executor/claude_executor.go)
- **Dojrzałość:** 53 618 gwiazdek, push 2026-09-30, release **v8.0.4 z 2026-09-29**. Wysoka aktywność całego projektu nie jest dowodem stabilności abonamentowej ścieżki Claude w konkretnym stacku. — [Metadane](https://api.github.com/repos/router-for-me/CLIProxyAPI), [release](https://github.com/router-for-me/CLIProxyAPI/releases/tag/v8.0.4)

#### 5. eysenfalk/opencode-claude-subscription — lekka integracja V2, ale OAuth impersonation

- **Mechanizm:** native V2 integration + `http.request`/`http.response`, pozostawia wbudowany provider `anthropic`, dodaje logowanie OAuth lub reuse credentials Claude. Modyfikuje identity/headers i aliasy narzędzi, potem wysyła HTTP bez uruchamiania CLI do generacji. — [README diagram/mechanism](https://github.com/eysenfalk/opencode-claude-subscription#how-it-works)
- **Task/MCP:** OpenCode nadal wykonuje własne narzędzia po odwróceniu aliasów. MCP-shaped aliases są reprezentacją nazw, nie osobną pętlą narzędzi Claude. Architektonicznie DeepSeek per rola pozostaje możliwy. — [Wire changes](https://github.com/eysenfalk/opencode-claude-subscription#what-changes-on-the-wire), [OpenCode task](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts)
- **Dojrzałość:** 1 gwiazdka, push 2026-09-28, release **v0.1.4 z 2026-09-28**. Autor testował OpenCode 2.0.16/SDK 2.0.18 i Haiku z tool round-trip; inne modele, w tym Opus, są oznaczone jako niezweryfikowane. Reuse login działał end-to-end, browser flow sprawdzono tylko do URL autoryzacji. — [Metadane](https://api.github.com/repos/eysenfalk/opencode-claude-subscription), [release](https://github.com/eysenfalk/opencode-claude-subscription/releases/tag/v0.1.4), [tested with](https://github.com/eysenfalk/opencode-claude-subscription#tested-with)
- README porównuje zachowanie system promptu z griffinmartin, ale bez przypięcia porównania do konkretnego commita. ## 3. Czy plugin usuwa potrzebę natywnej integracji Claude Code w Paseo?

### Takeaway

**Warunkowo tak na poziomie interfejsu Paseo:** provider-bridge, który zachowuje OpenCode tools, może zostawić Paseo podłączone wyłącznie do OpenCode. **Nie usuwa zależności od Claude Code runtime/auth**, a worker-plugin nie gwarantuje głównego Opusa z natywnymi subagentami DeepSeek. — [Krowli architecture](https://github.com/Krowli/opencode-claude-bridge), [Antonio architecture](https://github.com/AntonioAEMartins/claude-code-proxy#how-it-works), [leohenon limitations](https://github.com/leohenon/opencode-claude-cli/blob/master/README.md#limitations)

### Cited Findings

- Docelowy łańcuch zgodny z architekturą Krowli wygląda tak: **Paseo → OpenCode → provider bridge → Claude CLI/SDK → Opus**, a narzędzia wracają do OpenCode; **OpenCode native task → context-scout-fast → osobny provider DeepSeek**. Hook pluginu Krowli jest scoped do Claude providera, więc nie musi obsługiwać żądań DeepSeek. Część Paseo jest założeniem użytkownika; dalszy łańcuch wynika z implementacji mostu i wyboru modelu subagenta. — [Scoped hook](https://github.com/Krowli/opencode-claude-bridge/blob/main/plugin/opencode-claude-proxy.ts), [Tools bridge](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/lib/proxy.ts), [Native model resolution](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts)
- Plugin **leohenon** pozwala wybrać Claude model w UI OpenCode, ale prowadzi wykonanie w harness-ie Claude, z Claude-side MCP i textual tool transcript. To usuwa potrzebę osobnego widoku Claude w UI tylko w ograniczonym znaczeniu; nie zachowuje badanego kontraktu natywnych ról. — [README](https://github.com/leohenon/opencode-claude-cli/blob/master/README.md), [buildPrompt](https://github.com/leohenon/opencode-claude-cli/blob/master/src/claude-cli.ts)
- Plugin **Julian** dodaje jawne narzędzie wywołania Claude. Może być workerem dla innego głównego modelu, ale sam nie dostarcza głównego Opusa jako pełnego providera OpenCode. — [Current limitations](https://github.com/JulianBeaulieu/opencode-claude-bridge#current-limitations)
- Adapter **Claude ACP** to możliwość wystawienia osobnego agenta klientowi ACP. OpenCode również ma serwer ACP; z tych dwóch faktów nie wynika gotowy provider Claude-under-OpenCode. To inna topologia niż użytkownik chce zachować. — [OpenCode ACP docs](https://opencode.ai/docs/acp/), [Claude ACP README](https://github.com/agentclientprotocol/claude-agent-acp)
- Bezpośrednie pluginy **OAuth** pozwalają OpenCode zachować tools i role bez CLI do każdej generacji, ale używają tokenów/HTTP po swojej stronie. To nie jest dowód, że można bezproblemowo zastąpić oficjalną integrację Claude abonamentowym providerem. — [Griffin technical](https://github.com/griffinmartin/opencode-claude-auth#how-it-works-technical), [eysenfalk mechanism](https://github.com/eysenfalk/opencode-claude-subscription#how-it-works)

### Inferences

- Najkrótsza odpowiedź dla użytkownika: **„Jest gotowy plugin, który ma właściwą architekturę i może zostawić Paseo → OpenCode, ale nie ma tu potwierdzonego, dojrzałego drop-in dla Twojego konkretnego stacku. Krowli jest najbardziej obiecujący; Antonio jest alternatywą proxy. Większość innych ‘Claude Code providers’ oddaje pętlę Claude albo nadal robi direct OAuth.”** — [Krowli requirements](https://github.com/Krowli/opencode-claude-bridge#requirements), [Antonio bridge](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/tools/mcp-bridge.ts), [leohenon](https://github.com/leohenon/opencode-claude-cli/blob/master/README.md), [CLIProxyAPI executor](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/runtime/executor/claude_executor.go)
- Dowód potrzebny przed uznaniem celu za spełniony: zaobserwowany OpenCode-native tool event delegowania, child session z rzeczywistym provider/model DeepSeek, powrót jego wyniku do sesji Opus oraz brak wykonania zastępczego Claude-native Task. Wymóg wynika z różnicy obu modeli harness-u, nie z samego pojawienia się Opusa w model pickerze. — [OpenCode task.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/task.ts), [leohenon display-only tools](https://github.com/leohenon/opencode-claude-cli/blob/master/README.md), [Krowli mocked round-trip](https://github.com/Krowli/opencode-claude-bridge/blob/main/proxy/test/parallel-tools-regression.ts)

### Gaps

- Brak testu działania przez Paseo, informacji o wspieranej przez użytkownika generacji OpenCode i środowisku logowania Claude. Nie potwierdzono, czy proces serwera startowany przez Paseo ma środowisko/session access wymagane przez Krowli.
- Brak testu realnych MCP użytkownika, przerwania zadania, restartu proxy, compaction i długiego działania roli DeepSeek. Repo Krowli zawiera regression tests dla części tych stanów, ale nie zostały tu uruchomione. — [Test suite](https://github.com/Krowli/opencode-claude-bridge/tree/main/proxy/test)
- Nie ma podstaw do obiecywania braku dodatkowego rozliczenia ani określonej częstotliwości ograniczeń konta. Wykorzystano oficjalną dokumentację polityki SDK i jawne opisy mechanizmów, bez proponowania obchodzenia identyfikacji klienta. — [Anthropic SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
